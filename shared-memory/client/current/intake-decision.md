# Intake Decision: 小儀

**Decision date**: 2026-05-25  
**Decided by**: COO

## 三問判斷

### Q1：客戶是否卡在「兩個領域中間」？

**Yes。** 企管 + 資工輔修 + 想申請量化研究方向碩士。她正卡在「商管研究方法 + 技術實作」的中間地帶——傳統商學院學長姐告訴她「硬讀」，傳統工程同學告訴她「寫個 RAG」，兩邊都不完整。

### Q2：客戶想動手嗎？

**想動手，且打算給自己天天用。** 她明確說「不是要做產品」，但要「自己會天天用的工具」。這比一般客戶更高——是要做出來真用，不只是 demo 給人看。

照原本標準，這應該歸「過鏟組」（需要試刀）。但她有自我使用的迴圈（自己會用 = 自我測試），且時程只有 7 天，外部測試者來不及調度。

**決定：全鏟組，註記「客戶自己即測試者」。** 試刀人這次不啟動，但鑿井匠交稿時要交代「自我測試 checklist」給客戶，讓她在 6/2 meeting 前自己跑一次。

### Q3：48 小時內我能不能交一份對她有用的下一步？

**能。** 路線測繪師可以在 24 hr 內交路線圖。鑿井匠在 5/27-5/31 陪跑 hello world 到第一個能跑的 demo。6/1 deliverable 整合完成，留 6/1 一整天給客戶自己測試。

## 派工順序

1. 路線測繪師：5/25-5/26（24 hr）
2. 鑿井匠：5/27-5/31（5 天，含陪跑）
3. COO 整合 deliverable：6/1

## 對客戶的特殊註記

- 她預計 6/2 跟指導老師 meeting → deliverable 一頁總結要寫到「指導老師也能 30 秒看完」的程度
- 她讀 paper 的脈絡記憶需求 → 鑿井匠的 SDK 選擇需考慮「能維持研究主題 context」（建議 Claude Agent SDK + 簡單的 memory layer，或 LangGraph 的 state）

## 不接的理由（不適用）

無。本案接受。
